## RAG Improvement Insights

### Identified Weaknesses

- **Complex/Planning Queries (impact-complex, -4pts)**: MCP retrieval returned narrowly-focused code chunks that caused the model to produce a less comprehensive implementation guide compared to using its full context window.
  - **Root Cause Hypothesis**: Chunking strategy splits implementation patterns across many small chunks; retrieval returns partial views instead of complete class hierarchies needed for "how to add X" questions.
  - **Affected Component**: Chunking strategy, retrieval ranking (packages/core)

- **Edge-Case/Broad Analysis (error-edge-case, -2pts)**: Retrieved context displaced existing valuable context without adding proportional value for broad analytical questions.
  - **Root Cause Hypothesis**: No query-type classification — broad analytical queries get the same retrieval strategy as narrow factual queries. For broad questions, retrieval can introduce noise.
  - **Affected Component**: Query routing / retrieval strategy (packages/mcp-server)

- **Architectural Queries (arch-semantic, 0pts)**: MCP added no value for high-level architecture questions.
  - **Root Cause Hypothesis**: Architecture understanding requires module-level relationships, not code-level chunks. The index lacks a "module summary" layer.
  - **Affected Component**: Indexing pipeline — missing architectural summary layer (packages/core)

### Proposed Improvements (Prioritized)

| #   | Improvement                                        | Affected Package    | Effort | Expected Impact                                            |
| --- | -------------------------------------------------- | ------------------- | ------ | ---------------------------------------------------------- |
| 1   | Query-type classification with adaptive retrieval  | packages/mcp-server | M      | Fix regressions on complex/broad queries (+4-6pts)         |
| 2   | Hierarchical chunking (class-level + method-level) | packages/core       | M      | Improve complex planning queries (+3-4pts)                 |
| 3   | Module-level architectural summaries               | packages/core       | S      | Improve arch-semantic category (+1-2pts)                   |
| 4   | Confidence-gated retrieval (skip if low relevance) | packages/mcp-server | S      | Prevent regressions on queries where context is sufficient |
| 5   | Dependency-aware chunk expansion                   | packages/core       | L      | Improve cross-file and impact queries (+2-3pts)            |

**Details:**

1. **[P1] Query-Type Classification with Adaptive Retrieval**
   - **Problem**: MCP retrieval hurt quality on complex planning and broad analytical queries by returning narrow chunks that displaced better context.
   - **Proposed Solution**: Classify incoming queries (factual, planning, analytical, negative) and adjust retrieval strategy: fewer chunks for broad queries, more chunks with dependency expansion for planning queries, and "confirm absence" mode for negative queries.
   - **Affected Package**: packages/mcp-server
   - **Expected Impact**: Eliminate the -4pt and -2pt regressions; overall average improvement from +3.4% to +8-10%
   - **Effort Estimate**: Medium
   - **GSD Phase Goal**: Implement query classifier that routes to different retrieval strategies based on intent

2. **[P2] Hierarchical Chunking (Class-Level + Method-Level)**
   - **Problem**: For "how to add a new X" questions, the model needs complete class structures and pattern examples, not individual method chunks.
   - **Proposed Solution**: Index at two granularities — class-level chunks (full class with method signatures) and method-level chunks (implementation detail). Use class-level for planning queries, method-level for specific function questions.
   - **Affected Package**: packages/core (indexer, chunking)
   - **Expected Impact**: +3-4 points on impact-complex category
   - **Effort Estimate**: Medium
   - **GSD Phase Goal**: Dual-granularity indexing with class-level and method-level chunks

3. **[P3] Module-Level Architectural Summaries**
   - **Problem**: Architecture questions got no benefit from retrieval because the index only contains code chunks, not module relationship summaries.
   - **Proposed Solution**: During indexing, generate and store module-level summaries (dependencies, public API surface, key patterns) as retrievable documents. Use these for architectural queries.
   - **Affected Package**: packages/core (indexer)
   - **Expected Impact**: +1-2 points on arch-semantic; provides grounded architectural context
   - **Effort Estimate**: Small
   - **GSD Phase Goal**: Auto-generate module summary documents during indexing

4. **[P4] Confidence-Gated Retrieval**
   - **Problem**: MCP always injects retrieved context even when it's lower quality than what's already available, causing regressions.
   - **Proposed Solution**: Score retrieval results for relevance confidence; if below threshold, return a "no additional context needed" signal instead of injecting potentially harmful noise.
   - **Affected Package**: packages/mcp-server
   - **Expected Impact**: Prevent regressions (convert -2/-4 to 0); protect quality floor
   - **Effort Estimate**: Small
   - **GSD Phase Goal**: Add relevance threshold gate that suppresses low-confidence retrievals

5. **[P5] Dependency-Aware Chunk Expansion**
   - **Problem**: Cross-file queries require understanding how classes relate through imports/inheritance, but current retrieval treats chunks independently.
   - **Proposed Solution**: When retrieving a chunk, automatically include its direct dependency graph (imports, parent classes, implemented interfaces) to provide complete implementation context.
   - **Affected Package**: packages/core (retrieval, dependency graph)
   - **Expected Impact**: +2-3 points on cross-file and complex categories
   - **Effort Estimate**: Large
   - **GSD Phase Goal**: Expand retrieved chunks with dependency context from the indexed graph

### RAG Pipeline Health Score

- **Retrieval Relevance**: 6/10 — Good for keyword/factual queries, poor for broad/complex queries. Negative query handling is strong.
- **Context Quality**: 5/10 — Chunks are too narrow for planning tasks; no hierarchical representation exists.
- **Response Integration**: 7/10 — When retrieval is relevant, the model integrates it well (see +8pt gain on negative queries).
- **Overall RAG Health**: 6/10

### Priority Recommendation

> Implement query-type classification to route broad/planning queries away from standard chunk retrieval, preventing the -4pt regression on complex queries while preserving the +8pt gain on negative/factual queries.

## Recommendations

### Should MCP remain enabled?

**YES** — MCP is cost-neutral, 33% faster on average, and provides net quality improvement (+3.4%). The decisive +8pt win on negative queries and +3pt win on keyword queries demonstrate clear value for specific query types. The regressions on complex/broad queries are addressable through the improvements above.

### Prompt categories where MCP adds most value

1. **Negative/absence queries** (+8pts) — Confirming what doesn't exist and providing alternatives
2. **Keyword/factual queries** (+3pts) — Finding specific code paths and implementations
3. **Cross-file dependencies** (neutral) — No harm, potential for improvement

### Prompt categories where MCP currently hurts

1. **Complex planning queries** (-4pts) — Multi-file implementation guides
2. **Broad analytical queries** (-2pts) — Codebase-wide pattern analysis

### Potential RAG pipeline improvements

See Section 6 above for prioritized list. Top priority: query-type classification.

### Suggested next steps

1. Implement P4 (confidence-gated retrieval) as a quick win to eliminate regressions
2. Implement P1 (query classification) for the largest quality uplift
3. Re-run benchmark after improvements to validate
4. Expand benchmark corpus with more complex/planning prompts to stress-test improvements
