## RAG Improvement Insights

### Identified Weaknesses

- **Code References (keyword prompts)**: MCP responses lacked actual code snippets and line numbers that the non-MCP baseline included
  - **Root Cause Hypothesis**: RAG retrieval returns semantic summaries/chunks but not precise file locations with line numbers
  - **Affected Component**: Chunking strategy, retrieval result formatting

- **Negative-Case Handling**: MCP added latency and tokens searching for features that don't exist
  - **Root Cause Hypothesis**: No early-exit mechanism when search results return empty/low-confidence matches
  - **Affected Component**: MCP tool orchestration, confidence thresholds

- **Simple Lookup Overhead**: For "find X in file Y" questions, MCP's search-then-retrieve pattern is slower than direct file access
  - **Root Cause Hypothesis**: No query classification to skip RAG for simple lookups
  - **Affected Component**: MCP server query routing

### Proposed Improvements (Prioritized)

| #   | Improvement                   | Affected Package    | Effort | Expected Impact                                                    |
| --- | ----------------------------- | ------------------- | ------ | ------------------------------------------------------------------ |
| 1   | Query complexity classifier   | packages/mcp-server | M      | Skip RAG for simple lookups, save 400%+ latency on keyword queries |
| 2   | Line-number-aware chunking    | packages/core       | M      | +2 pts on code reference dimensions                                |
| 3   | Confidence-based early exit   | packages/mcp-server | S      | Reduce negative-case latency by 80%                                |
| 4   | Preflight tool implementation | packages/benchmark  | S      | Enable proper benchmark orchestration                              |
| 5   | Hybrid retrieval tuning       | packages/core       | L      | Balance semantic vs keyword for cross-file tracing                 |

**Details:**

1. **[P1] Query Complexity Classifier**
   - **Problem**: MCP adds 400%+ latency on simple keyword lookups (11s → 57s) with worse quality
   - **Proposed Solution**: Classify incoming queries as simple-lookup vs. analytical. For simple lookups, use direct file access tools; for analytical, use full RAG pipeline.
   - **Affected Package**: packages/mcp-server
   - **Expected Impact**: Eliminate regression on keyword/function-lookup prompts (-3pts → 0pts), reduce average latency
   - **Effort Estimate**: Medium
   - **GSD Phase Goal**: Implement query intent classifier that routes simple lookups to direct file access

2. **[P2] Line-Number-Aware Chunking**
   - **Problem**: MCP responses lack precise file:line references that judges (and developers) value
   - **Proposed Solution**: Include source file path and line range in chunk metadata; format retrieval results with `file.java:L42-L58` references
   - **Affected Package**: packages/core (indexer)
   - **Expected Impact**: +1-2 pts on Code References dimension across all prompt types
   - **Effort Estimate**: Medium
   - **GSD Phase Goal**: Embed line number ranges in chunk metadata and surface them in MCP tool responses

3. **[P3] Confidence-Based Early Exit**
   - **Problem**: Negative-case prompts waste tokens searching for absent features
   - **Proposed Solution**: When search_codebase returns 0 results or all results have similarity < 0.3, return "not found" immediately without additional tool calls
   - **Affected Package**: packages/mcp-server
   - **Expected Impact**: 80% latency reduction on negative-case queries, prevent hallucination risk
   - **Effort Estimate**: Small
   - **GSD Phase Goal**: Add confidence threshold to MCP search tools with early-exit on low-confidence results

4. **[P4] Preflight Tool Implementation**
   - **Problem**: benchmark_preflight tool doesn't exist, blocking proper benchmark orchestration
   - **Proposed Solution**: Implement the tool in the MCP server to validate tool availability and provide pre-retrieval context hints
   - **Affected Package**: packages/benchmark, packages/mcp-server
   - **Expected Impact**: Enable proper A/B benchmarking with orchestrated retrieval
   - **Effort Estimate**: Small
   - **GSD Phase Goal**: Implement benchmark_preflight MCP tool for benchmark orchestration

5. **[P5] Hybrid Retrieval Tuning**
   - **Problem**: Cross-file dependency tracing (-1pt) suggests semantic search alone misses structural relationships
   - **Proposed Solution**: Combine semantic similarity with AST-based dependency graph traversal for cross-file queries
   - **Affected Package**: packages/core
   - **Expected Impact**: +1-2 pts on cross-file dependency questions
   - **Effort Estimate**: Large
   - **GSD Phase Goal**: Integrate AST dependency graph with vector search for relationship-aware retrieval

## Recommendations

### Should MCP remain enabled?

**YES, conditionally.** MCP demonstrates clear value on architectural/analytical questions (+4 pts) and dramatic efficiency gains on complex questions (94.8% token reduction). However, it regresses on simple lookups. The recommendation is to keep MCP enabled but implement query routing (P1) to avoid regression on simple queries.

### Prompt categories where MCP adds most value

1. **Architectural/semantic** — understanding module interactions, system design
2. **Complex/impact analysis** — what-if scenarios requiring cross-cutting knowledge
3. **Pattern analysis** — error handling, coding conventions, consistency checks

### Prompt categories where MCP adds least/negative value

1. **Keyword/function lookups** — "find X" questions where direct file access is faster
2. **Negative-case questions** — checking for absence of features
3. **Cross-file tracing** — marginal, needs dependency-graph enhancement

### Potential RAG pipeline improvements

1. Query classification to skip RAG for simple lookups (highest impact)
2. Line-number metadata in chunks for precise code references
3. Confidence thresholds to short-circuit negative-case searches
4. AST-based dependency graph for cross-file relationship queries

### Suggested next steps

1. Implement `benchmark_preflight` tool to enable proper orchestrated benchmarking
2. Build query complexity classifier (P1) — highest ROI improvement
3. Re-run benchmark after P1 implementation to measure regression elimination
4. Add more prompt categories (refactoring, testing, debugging) for broader coverage
