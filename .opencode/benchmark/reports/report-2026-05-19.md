## Executive Summary

**Overall Verdict: WITHOUT MCP wins 141 vs 131 (+10 points), BUT result is unreliable due to judge error on Prompt 5.**

The benchmark ran 6 prompts comparing responses with and without MCP-enhanced RAG retrieval. Raw scores favor WITHOUT MCP (3 wins vs 2 wins, 1 tie). However, Prompt 5 contains a confirmed judge evaluation error worth ~12+ points of swing — the judge penalized the WITH MCP response for describing a Java payment gateway, which IS the actual target project. If corrected, results likely reach parity or slight MCP advantage.

Key findings:

- MCP adds value for **cross-file tracing** (Prompt 3: +4pts) and **architecture overview** (Prompt 1: +2pts)
- MCP shows weakness on **keyword/domain-specific queries** (Prompt 2: -5pts) where baseline context was sufficient
- MCP adds ~13.2% more input tokens at ~8.5% more latency — modest overhead
- 2 blocked tools (get_module_dependencies, query_database) may have impacted cross-file and persistence queries

## RAG Improvement Insights

### Identified Weaknesses

- **Retrieval Relevance (Prompt 2)**: MCP retrieved 12K extra tokens but missed key domain flows that the baseline had. The retrieval prioritized breadth over the specific "entry processing" domain logic.
  - **Root Cause Hypothesis**: Chunking strategy splits domain logic across chunks, and semantic search doesn't rank "processing flow" chunks high enough vs. tangentially related code
  - **Affected Component**: Embedding model relevance ranking, chunk boundaries

- **Response Time Variance (Prompts 5, 6)**: 5-10x latency increase on some queries
  - **Root Cause Hypothesis**: Retrieval queries that match many low-relevance chunks cause excessive context assembly
  - **Affected Component**: Retrieval threshold/top-k configuration

- **Negative Query Handling (Prompt 5)**: When the answer is "no, this doesn't exist," MCP still retrieves and injects context, potentially confusing the LLM
  - **Root Cause Hypothesis**: No "confidence gate" — system always retrieves regardless of query type
  - **Affected Component**: Query classification / retrieval decision logic

- **Complex Multi-step Queries (Prompt 4)**: Tie despite extra context — blocked `get_module_dependencies` limited value
  - **Root Cause Hypothesis**: Missing dependency graph tool prevented showing integration points
  - **Affected Component**: Tool availability (infrastructure)

### Proposed Improvements (Prioritized)

| #   | Improvement                                       | Affected Package    | Effort | Expected Impact                                           |
| --- | ------------------------------------------------- | ------------------- | ------ | --------------------------------------------------------- |
| 1   | Fix judge target-project context                  | packages/benchmark  | S      | Eliminates false negatives in evaluation                  |
| 2   | Add retrieval confidence gate                     | packages/mcp-server | M      | Reduces false retrieval on negative queries, cuts latency |
| 3   | Improve chunk boundary detection for domain flows | packages/core       | M      | +2-3pts on keyword/domain queries                         |
| 4   | Add top-k adaptive threshold                      | packages/core       | S      | Reduces latency variance, prevents context dilution       |
| 5   | Restore get_module_dependencies tool              | packages/mcp-server | M      | +2pts on complex integration queries                      |
| 6   | Query-type classification pre-retrieval           | packages/mcp-server | L      | Better handling of all query types                        |

**Details:**

1. **[P1] Fix Judge Target-Project Context**
   - **Problem**: Judge evaluated responses against wrong technology stack, invalidating Prompt 5 results entirely
   - **Proposed Solution**: Include target project metadata (language, framework, key technologies) in judge system prompt. Add a "target_project_stack" field to benchmark config.
   - **Affected Package**: packages/benchmark
   - **Expected Impact**: Eliminates false scoring errors. Critical for benchmark validity.
   - **Effort Estimate**: Small
   - **GSD Phase Goal**: Ensure judge evaluates against correct target project context

2. **[P2] Retrieval Confidence Gate**
   - **Problem**: MCP retrieves context even for negative queries ("Does this use WebSocket?"), adding latency without value
   - **Proposed Solution**: Pre-classify query intent (existence check, how-to, architecture). For existence queries with low retrieval confidence scores, return "no relevant code found" instead of injecting marginal matches.
   - **Affected Package**: packages/mcp-server
   - **Expected Impact**: -50% latency on negative queries, +2pts quality on negative queries
   - **Effort Estimate**: Medium
   - **GSD Phase Goal**: Skip retrieval when confidence is below threshold for existence queries

3. **[P3] Domain-Aware Chunk Boundaries**
   - **Problem**: Entry processing flow spans multiple methods/classes but gets split across chunks, losing flow coherence
   - **Proposed Solution**: Use AST-aware chunking that keeps complete method bodies together. Add "flow markers" that link related chunks (e.g., caller -> callee).
   - **Affected Package**: packages/core (indexer)
   - **Expected Impact**: +3pts on domain-flow queries (P2-type), better retrieval precision
   - **Effort Estimate**: Medium
   - **GSD Phase Goal**: Chunk at method/class boundaries preserving complete domain flows

4. **[P4] Adaptive Top-K with Score Threshold**
   - **Problem**: Fixed top-k retrieves low-relevance chunks that dilute context (P2: +12K tokens, worse score)
   - **Proposed Solution**: Return top-K results only if similarity score > dynamic threshold. Cap injected context at N tokens.
   - **Affected Package**: packages/core (retrieval)
   - **Expected Impact**: -20% avg input tokens, +1-2pts by reducing noise
   - **Effort Estimate**: Small
   - **GSD Phase Goal**: Only inject retrieved chunks above adaptive relevance threshold

5. **[P5] Restore Module Dependencies Tool**
   - **Problem**: `get_module_dependencies` blocked, limiting cross-module integration queries
   - **Proposed Solution**: Debug and fix the tool's connection/permissions issue. Add health check to preflight.
   - **Affected Package**: packages/mcp-server
   - **Expected Impact**: +2pts on complex integration queries
   - **Effort Estimate**: Medium
   - **GSD Phase Goal**: All MCP tools passing preflight with zero blocked

6. **[P6] Query-Type Classification**
   - **Problem**: All queries treated identically regardless of intent (negative, keyword, semantic, cross-file)
   - **Proposed Solution**: Lightweight LLM classifier categorizes query → selects retrieval strategy (semantic search, keyword search, dependency graph, or skip)
   - **Affected Package**: packages/mcp-server
   - **Expected Impact**: +2pts average across all query types
   - **Effort Estimate**: Large
   - **GSD Phase Goal**: Route queries to optimal retrieval strategy based on intent classification

## Recommendations

### Should MCP remain enabled?

**YES, conditionally.**

Excluding the judge-error prompt, MCP reaches parity with clear wins on cross-file and architecture queries. The +12.5% cost overhead is acceptable given the value on complex queries. However, improvements P1-P4 above should be implemented to make MCP consistently beneficial.

### Prompt categories where MCP adds most value

1. **Cross-file tracing** (persistence, data flow): +4 pts
2. **Architectural overview** (system-level understanding): +2 pts
3. **Integration questions** (potential, limited by blocked tools)

### Prompt categories where MCP adds least/negative value

1. **Keyword/domain queries** where baseline context is already optimal: -5 pts
2. **Negative/existence queries**: latency cost without quality gain
3. **Edge-case queries** with sufficient baseline context: -1 pt

### Suggested next steps

1. **Immediate**: Fix judge evaluation to include target project stack metadata
2. **Short-term**: Implement adaptive top-k threshold to reduce context dilution
3. **Medium-term**: Add retrieval confidence gate for negative queries
4. **Medium-term**: Restore blocked tools and improve AST-aware chunking
5. **Re-benchmark**: After P1-P4, re-run the same 6 prompts to measure improvement
