## Executive Summary

The MCP-enhanced RAG pipeline delivers **+2.0 quality points on average** (23.0 → 25.0 out of 30, +8.7%) while being **34% faster** (98.7s → 65.2s average). The win distribution is 3-3, but MCP's wins are larger in magnitude (+10, +5, +2) compared to without-MCP wins (+3, +1, +1). MCP excels at architecture discovery, impact analysis, and negative questions; without-MCP performs better on detailed edge-case analysis and questions where broad context naturally produces complete answers.

**Net assessment**: MCP should remain enabled. The quality improvement is concentrated in the hardest query types (complex impact analysis, negative probing), which are the highest-value developer questions.

## RAG Improvement Insights

### Identified Weaknesses

- **Actionability (edge-case)**: MCP response lacked concrete recommendations section despite having code access
  - **Root Cause Hypothesis**: Retrieval focuses on "what exists" but doesn't prompt the LLM to synthesize improvement suggestions
  - **Affected Component**: MCP tool response formatting / prompt template

- **Completeness (keyword/cross-file)**: MCP sometimes retrieves narrower context than needed for end-to-end flow questions
  - **Root Cause Hypothesis**: Chunking boundaries may split logical flows; dependency graph expansion (2 hops) may not capture full transaction lifecycles
  - **Affected Component**: indexer chunking strategy, dependency graph traversal

- **Cross-file tracing**: Without-MCP scored higher on questions requiring following a data path across multiple layers
  - **Root Cause Hypothesis**: The retrieval limit returns top-N chunks but may miss middle layers of a call chain
  - **Affected Component**: retrieval ranking, call-chain traversal

### Proposed Improvements (Prioritized)

| #   | Improvement                                                 | Affected Package    | Effort | Expected Impact                           |
| --- | ----------------------------------------------------------- | ------------------- | ------ | ----------------------------------------- |
| 1   | Call-chain traversal tool                                   | packages/mcp-server | M      | +2-3pts on cross-file, keyword categories |
| 2   | "What exists instead" prompt injection for negative queries | packages/mcp-server | S      | Maintain +10pt advantage consistently     |
| 3   | Actionability post-processing hint                          | packages/mcp-server | S      | +2pts on edge-case category               |
| 4   | Larger chunk overlap for flow-based code                    | packages/core       | M      | +1-2pts on keyword, cross-file            |
| 5   | Transaction-boundary-aware chunking                         | packages/core       | L      | +2pts on cross-file, complex              |

**Details:**

1. **[P1] Call-Chain Traversal Tool**
   - **Problem**: MCP retrieves individual chunks but can't trace a full request lifecycle (controller → service → repository → DB)
   - **Proposed Solution**: Add an MCP tool `trace_call_chain` that, given a method/class, walks the dependency graph following invocations across layers, returning the full path
   - **Affected Package**: packages/mcp-server, packages/core (graph queries)
   - **Expected Impact**: +2-3pts on cross-file and keyword categories where end-to-end flow matters
   - **Effort Estimate**: medium
   - **GSD Phase Goal**: Implement call-chain traversal tool that returns ordered sequence of code from entry point to data layer

2. **[P2] Actionability Prompt Hint**
   - **Problem**: MCP responses describe what exists but don't prompt recommendations/improvements
   - **Proposed Solution**: When query intent is "patterns" or "analysis", append a system hint: "After describing findings, provide concrete recommendations for improvement"
   - **Affected Package**: packages/mcp-server (tool response templates)
   - **Expected Impact**: +2pts on edge-case and analysis queries
   - **Effort Estimate**: small
   - **GSD Phase Goal**: Add intent-aware response hints that guide LLM toward actionable output

3. **[P3] Transaction-Boundary-Aware Chunking**
   - **Problem**: Spring `@Transactional` methods and their call targets get split across chunks
   - **Proposed Solution**: Use AST analysis to detect transaction boundaries and ensure the full transactional unit stays in one chunk (or linked chunks)
   - **Affected Package**: packages/core (indexer, chunking)
   - **Expected Impact**: +2pts on cross-file and complex categories
   - **Effort Estimate**: large
   - **GSD Phase Goal**: Chunk Spring service classes by transactional boundary rather than fixed line count

## Recommendations

### Should MCP remain enabled?

**YES** — MCP delivers +8.7% quality improvement at no additional cost, with 34% faster responses. The largest gains (+10pts on negative questions, +5pts on complex impact analysis) occur on the highest-value developer queries.

### Prompt categories where MCP adds most value

1. **Negative probing** (Does X exist?) — decisive advantage
2. **Complex impact analysis** (What to modify?) — clear advantage
3. **Architecture overview** — narrow advantage

### Prompt categories where MCP underperforms

1. **Edge-case analysis** — needs actionability hints
2. **End-to-end flow tracing** — needs call-chain traversal

### Suggested next steps

1. Implement call-chain traversal tool (P1) to address cross-file weakness
2. Add response hint injection for analysis queries (P2) — quick win
3. Re-run benchmark after P1+P2 to measure improvement
4. Consider transaction-boundary chunking (P3) for Spring-specific projects
