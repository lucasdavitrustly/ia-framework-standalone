Relatório Comparativo: Spec-Driven Development

Análise para codebase legada, 12 devs, sprints multi-assunto, branch master → DEV

Contexto do Time

  • Codebase: Extensa e legada, alterada por múltiplos times

  • Fluxo Git: Branch de master → desenvolvimento → PR para DEV
  • Sprints: Itens diversos de diferentes assuntos tratados em paralelo
  • Risco principal: Conflitos, falta de contexto compartilhado, divergência de padrões

3. Caso de Uso: "Implementar endpoint de relatório financeiro"

Dev Rafael cria branch de master, faz feature, abre PR para DEV. Enquanto isso, outros 11 devs fazem o mesmo com outros assuntos.

3.1 Com TLC Spec-Driven

1. Rafael: "Specify feature financial-report-endpoint" → Agente cria .specs/features/financial-report-endpoint/spec.md → Define requisitos AUTH-01, FIN-01, FIN-02... 2. Agente auto-dimensiona: Medium → Specify + Execute → Agente pula Design/Tasks (inline) 3. Rafael: "Implement" → Commits atômicos: feat(finance): add report endpoint PROBLEMA: .specs/project/STATE.md é compartilhado. Se Dev Maria edita STATE.md na branch dela → CONFLITO no merge para DEV. Não há mecanismo de isolamento entre features paralelas.

Pontos fortes

  • Zero cerimônia — conversa natural
  • Auto-sizing evita overhead
  • Brownfield mapping mapeia a codebase legada

Problemas no cenário

  • STATE.md compartilhado = conflitos de merge
  • "One feature per cycle" — não escala para 12 devs
  • Sem tracking de quem está fazendo o quê
  • Session handoff é individual, não de time

3.2 Com GitHub Spec Kit

1. Rafael: git checkout -b feat/financial-report (de master) 2. Rafael: specify init . --integration copilot --force (ou já inicializado no repo) 3. Rafael: /speckit.constitution (já existe — shared no repo) 4. Rafael: /speckit.specify "Endpoint de relatório financeiro..." → specs/042-financial-report/spec.md criado → Branch pode ser renomeada para 042-financial-report 5. Rafael: /speckit.clarify → refina requisitos 6. Rafael: /speckit.plan "API REST com Spring Boot, PostgreSQL..." → specs/042-financial-report/plan.md + research.md 7. Rafael: /speckit.tasks → tasks.md gerado 8. Rafael: /speckit.taskstoissues → Issues criadas no GitHub 9. Rafael: /speckit.implement → executa tasks com commits 10. Rafael: Abre PR para DEV ISOLAMENTO: Cada dev tem specs/NNN-feature/ próprio. Constitution (.specify/memory/) é read-only durante development. Conflitos são mínimos — specs ficam em folders separados.

Pontos fortes

  • Isolamento natural por folder numerado
  • Constitution garante padrões entre 12 devs
  • Tasks → GitHub Issues integra com board do time
  • Branch-per-feature alinha com fluxo master→DEV
  • Extensível (presets para enforcement do time)
  • Scripts bash automatizam setup

Problemas no cenário

  • 7 passos é burocrático para hotfixes/tasks simples
  • Dependência Python (uv) pode incomodar devs Java/.NET
  • Numeração sequencial (001, 042) pode conflitar se 2 devs criam spec ao mesmo tempo
  • Curva de aprendizado maior para 12 pessoas

3.3 Com OpenSpec

1. Rafael: git checkout -b feat/financial-report (de master) 2. Rafael: /opsx:propose financial-report-endpoint → openspec/changes/financial-report-endpoint/ criado: - proposal.md (por quê, o quê) - specs/ (requisitos e cenários) - design.md (abordagem técnica) - tasks.md (checklist de implementação) 3. Rafael: Revisa/itera os artefatos (edita livremente) 4. Rafael: /opsx:apply → Agente implementa tasks sequencialmente com commits 5. Rafael: /opsx:archive → Move para openspec/changes/archive/2026-05-26-financial-report/ 6. Rafael: Abre PR para DEV ISOLAMENTO: Cada change tem folder próprio. Sem phase gates rígidos — pode iterar em qualquer ordem. 12 devs podem ter 12 changes/ simultâneos sem conflito.

Pontos fortes

  • Isolamento perfeito por change folder
  • Filosofia "brownfield first" — feito para codebase legada
  • 3 comandos core (/propose, /apply, /archive) = fácil de ensinar
  • Fluid, não rígido — sem phase gates
  • TypeScript/Node.js — alinhado com ecosistema JS
  • Archive mantém histórico de decisões

Problemas no cenário

  • Sem conversão tasks→Issues (board management manual)
  • Projeto mais novo (v1.3.1), menos battle-tested enterprise
  • Telemetria ativa por padrão (pode ser bloqueio em empresa)
  • Sem mecanismo de "constitution" para enforçar padrões globais

Recomendação: GitHub Spec Kit

Para o cenário descrito — 12 devs, codebase legada, múltiplos times, fluxo branch→PR — o GitHub Spec Kit é a melhor escolha pelos seguintes motivos:

  • Isolamento por design: Cada feature vive em specs/NNN-feature/ — zero conflitos entre branches paralelas
  • Constitution: Garante que 12 devs sigam os mesmos padrões sem supervisão manual
  • Tasks → Issues: Converte breakdown em GitHub Issues — integração direta com board e sprint planning
  • Presets organizacionais: Pode criar um preset do time que enforce regras (ex: "toda spec precisa impacto em módulos adjacentes")
  • Branch-first workflow: Alinha perfeitamente com fluxo master→branch→PR para DEV
  • Backed by GitHub: 106k stars, 1003 commits, manutenção ativa, 30+ integrações de agente

Alternativa pragmática: OpenSpec

Se a curva de aprendizado for a maior preocupação e o time priorizar adoção rápida com mínima fricção, o OpenSpec é uma alternativa sólida. Seus 3 comandos core são triviais de ensinar. Porém, vocês perdem governança centralizada (constitution) e conversão automática para Issues.

Evitar: TLC Spec-Driven

Apesar de excelente para desenvolvedor solo ou dupla, o TLC Spec-Driven tem limitações fundamentais para 12 devs em paralelo: STATE.md compartilhado, restrição "one feature per cycle", e ausência de mecanismos de coordenação entre branches.

5. Plano de Adoção Sugerido (Spec Kit)

  1. Semana 1: Tech Lead instala Spec Kit no repo, cria Constitution com padrões do time
  2. Semana 2: 2-3 devs piloto usam o fluxo completo em features reais da sprint
  3. Semana 3: Cria preset customizado do time (templates de spec/plan ajustados)
  4. Semana 4: Rollout para os 12 devs com sessão de 30min demonstrando o workflow
  5. Ongoing: Constitution evolui com decisões arquiteturais do time
