# Plan 11-03: Hybrid Search — BM25 Sparse + Dense Vectors + RRF Fusion

**Phase**: 11 — MRR Quick Wins & Corpus Building

**Depends on**: 11-02 (text vector fix applied; re-index required before benchmarking but not before this plan)
**Estimated duration**: ~35 minutes
**Goal**: Add hybrid search combining BM25 sparse vectors with the existing dual dense vectors (text + code), fused via Reciprocal Rank Fusion (RRF). Exposed as a **new** `search_codebase_hybrid` MCP tool alongside the existing `search_codebase`.

---

## Context

### Why hybrid search?

The existing `search_codebase` tool uses dense vector similarity only. Dense search is great for semantic similarity but misses exact keyword matches (e.g. a query for "QdrantVectorStore" should retrieve the class by name, not just by semantic proximity).

BM25 sparse vectors capture term-frequency × inverse-document-frequency signal — exactly what makes keyword search work. RRF fusion combines sparse and dense rankings to get the best of both worlds without needing to tune weights.

**Expected impact**: +10–20% MRR, especially on `keyword` and `edge` category queries.

### How Qdrant implements BM25

Qdrant supports sparse vectors natively. When you create a collection with a named sparse vector and set `modifier: "idf"`, Qdrant stores the IDF statistics server-side. At query time:

1. Client computes a **term-frequency sparse vector** (TF only) from the query text: map each unique token to an integer index, value = term count.
2. Client sends `{ indices: [...], values: [...] }` as the sparse query vector via `prefetch.query.nearest`.
3. Qdrant multiplies TF values by its stored IDF weights → BM25 score.

The collection needs one new sparse vector slot named `"sparse"`. This **requires collection recreation** — existing points must be re-indexed after this plan (same re-index as required by 11-02).

### Qdrant 1.17.0 API used

```typescript
// Hybrid search via client.query() with prefetch + RRF
await client.query(collectionName, {
  prefetch: [
    { query: { nearest: denseVector }, using: 'text', limit: 20 },
    { query: { nearest: denseVector }, using: 'code', limit: 20 },
    { query: { nearest: sparseVector }, using: 'sparse', limit: 20 },
  ],
  query: { fusion: 'rrf' },
  limit: 10,
  with_payload: true,
});
```

`sparseVector` = `{ indices: number[], values: number[] }` — a `SparseVector` in Qdrant's schema.

### New MCP tool — NOT a parameter on existing tool

`search_codebase_hybrid` is a **separate MCP tool** from `search_codebase`. This lets OpenCode choose the tool explicitly and lets us evaluate each independently. The existing `search_codebase` is not modified.

      },

    limit: options.limit,

    score: r.score,
    payload: r.payload as ChunkPayload,
    vectorName: 'text' as const, // RRF fusion — no single vector name

}

```typescript
/**
 * Hybrid search combining dense text, dense code, and BM25 sparse vectors via RRF fusion.
 * Uses Qdrant's query() API with prefetch + RRF to combine rankings from all three vectors.
 *
 * Falls back to plain search() if the vector store does not support searchHybrid.
 *
 * @param query - RetrievalQuery (same type as search())
 */
async searchHybrid(query: RetrievalQuery): Promise<RetrievalResult[]> {
  const { embeddingProvider, vectorStore } = this.config;

  // Fall back to plain search if hybrid is not supported by this store
  if (!vectorStore.searchHybrid) {
    return this.search(query);
  }

  const limit = query.limit ?? this.config.defaultLimit ?? 10;

  // Embed the query text into a dense vector
  const denseVector = await embeddingProvider.embed(query.text);

  // Compute TF sparse vector from the query text (client-side BM25 input)
  const sparseVector = computeTermFrequencySparseVector(query.text);

  const results = await vectorStore.searchHybrid({
    denseVector,
    sparseVector,
    limit,
    filter: query.filter,
  });

  return results.map((raw) => toRetrievalResult(raw, 'both'));
}
```

**3c. Implement `computeTermFrequencySparseVector()`** (module-level helper):

```typescript
/**
 * Compute a term-frequency sparse vector from a text string.
 *
 * Tokenizes the text into lowercase alphanumeric tokens, counts occurrences,
 * and maps each unique token to a stable integer index using a simple hash.
 *
 * Qdrant applies IDF weighting server-side (modifier="idf") — we only need TF here.
 *
 * The hash function maps token strings to 32-bit integers in [0, 2^31-1].
 * Collision probability is negligible for short query strings (< 50 tokens).
 */
function computeTermFrequencySparseVector(text: string): { indices: number[]; values: number[] } {
  // Tokenize: lowercase, split on non-alphanumeric, filter short tokens
  const tokens = text
    .toLowerCase()
    .split(/[^a-z0-9]+/)
    .filter((t) => t.length >= 2);

  // Count term frequencies
  const tf = new Map<string, number>();
  for (const token of tokens) {
    tf.set(token, (tf.get(token) ?? 0) + 1);
  }

  // Map each token to a stable integer index using djb2 hash
  const entries: Array<[number, number]> = [];
  for (const [token, count] of tf) {
    const idx = djb2Hash(token);
    entries.push([idx, count]);
  }

  // Sort by index for Qdrant (indices must be sorted ascending)
  entries.sort((a, b) => a[0] - b[0]);

  return {
    indices: entries.map((e) => e[0]),
    values: entries.map((e) => e[1]),
  };
}

/**
 * djb2 hash — fast, simple, good distribution for short strings.
 * Returns a non-negative 31-bit integer.
 */
function djb2Hash(str: string): number {
  let hash = 5381;
  for (let i = 0; i < str.length; i++) {
    hash = ((hash << 5) + hash + str.charCodeAt(i)) >>> 0;
  }
  return hash & 0x7fffffff; // clamp to 31 bits (Qdrant max sparse index)
}
```

Export `computeTermFrequencySparseVector` from the module for testability (named export, not in the public index).

### Task 4: Implement `search_codebase_hybrid` MCP tool

**File**: `packages/mcp-server/src/tools/search-codebase-hybrid.ts` (new file)

```typescript
import { McpServer } from '@modelcontextprotocol/sdk/server/mcp.js';
import type { CallToolResult } from '@modelcontextprotocol/sdk/types.js';
import { z } from 'zod';
import type { RetrievalResult } from '@ia-framework/retrieval';

type HybridEngine = {
  searchHybrid(query: {
    text: string;
    limit?: number | undefined;
    filter?: Record<string, unknown> | undefined;
  }): Promise<RetrievalResult[]>;
  // Fallback: if searchHybrid is not available, we warn but do not crash
  search?(query: { text: string; limit?: number }): Promise<RetrievalResult[]>;
};

export interface SearchCodebaseHybridInput {
  query: string;
  limit?: number | undefined;
}

export type ToolOutput = CallToolResult;

/**
 * Format a single RetrievalResult as a markdown section.
 * Same format as search_codebase for consistency.
 */
function formatResult(result: RetrievalResult, index: number): string {
  const header = result.name
    ? `### ${index}. ${result.relativePath} (${result.name}) — score: ${result.score.toFixed(3)} [hybrid]`
    : `### ${index}. ${result.relativePath} — score: ${result.score.toFixed(3)} [hybrid]`;

  const codeBlock = `\`\`\`${result.language}\n${result.content}\n\`\`\``;
  return `${header}\n${codeBlock}`;
}

/**
 * Handle the search_codebase_hybrid tool call.
 * Exported separately for testability.
 */
export async function searchCodebaseHybridHandler(
  engine: HybridEngine,
  input: SearchCodebaseHybridInput,
): Promise<ToolOutput> {
  const results = await engine.searchHybrid({
    text: input.query,
    limit: input.limit ?? 10,
  });

  if (results.length === 0) {
    return {
      content: [
        {
          type: 'text',
          text: `No results found for query: "${input.query}"`,
        },
      ],
    };
  }

  const sections = results.map((r, i) => formatResult(r, i + 1));
  const text = `## Hybrid search results for: "${input.query}"\n\n${sections.join('\n\n')}`;

  return {
    content: [{ type: 'text', text }],
  };
}

/**
 * Register the search_codebase_hybrid tool on an MCP server.
 */
export function registerSearchCodebaseHybridTool(server: McpServer, engine: HybridEngine): void {
  server.registerTool(
    'search_codebase_hybrid',
    {
      description:
        'Search the indexed codebase using hybrid retrieval: BM25 sparse keyword search + dense semantic search, ' +
        'combined via Reciprocal Rank Fusion (RRF). ' +
        'Better than search_codebase for queries mixing exact identifiers with semantic concepts. ' +
        'Use search_codebase for pure semantic queries; use this tool when you know specific class/function names.',
      inputSchema: {
        query: z.string().describe('Natural language search query (can include exact identifiers)'),
        limit: z.number().optional().describe('Maximum number of results (default: 10)'),
      },
    },
    async (input) => {
      return searchCodebaseHybridHandler(engine, input);
    },
  );
}
```

## Notes

- **Collection recreation required**: Adding `sparse_vectors` to `createCollection` means existing collections (without the sparse slot) must be recreated. The existing dimension-mismatch recreation logic handles this — the executor can trigger re-indexing via `ia-framework index --full`. Document in the plan SUMMARY.
- **No score threshold for hybrid**: RRF fusion produces relative ranks, not absolute scores. The `score_threshold` parameter is omitted from `searchHybrid()` intentionally — RRF scores are not directly comparable to cosine similarity scores.
- **`as any` cast on `client.query()`**: The Qdrant JS client 1.17.0 types use destructured parameter syntax that TypeScript can't resolve well in all cases. Use `as any` with a clear comment — same pattern as `deleteByFilter`/`deleteByIds` in the existing code.
- **Sparse vector hash collisions**: The djb2 hash maps tokens to 31-bit integers. For a 5–15 token query, collision probability is negligible (<0.001%). If two tokens happen to collide their TF values will be summed — a harmless approximation for short queries.
- **`computeTermFrequencySparseVector` export location**: If adding it to `@ia-framework/retrieval/src/index.ts` causes a circular dependency, move it to `@ia-framework/core` instead. Check with `pnpm -w build` — the turbo dependency graph will surface any circularity.
