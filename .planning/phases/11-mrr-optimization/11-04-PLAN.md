# Plan 11-04: Threshold Tuning, Benchmark Comparison, and MCP Default Update

**Phase**: 11 — MRR Quick Wins & Corpus Building
**Plan**: 4 of 4
**Depends on**: 11-01 (corpus), 11-02 (text vector fix), 11-03 (hybrid + sparse)
**Estimated duration**: ~25 minutes
**Goal**: Run systematic threshold benchmarks after the full re-index, identify the optimal `scoreThreshold`, apply it as the MCP default, publish before/after MRR comparison, and close out Phase 11.

---

## Context

Plans 11-02 and 11-03 changed how vectors are stored in Qdrant:

- **11-02**: text vectors now embed prose descriptions (not raw code)
- **11-03**: collection now requires a `sparse` named sparse vector slot

Both changes require a **full re-index** (`ia-framework index --full`) before benchmark results are meaningful. Running benchmarks against stale vectors would produce incomparable results.

**This plan runs entirely after the re-index.** The executor must trigger and wait for the re-index to complete before running any benchmark commands.

### Why threshold matters

The current MCP default is `scoreThreshold: 0.5` (hardcoded in `search-codebase.ts:64`). This was set heuristically in Phase 3. After the text vector fix, the cosine similarity score distribution for the `text` vector will shift (prose embeddings have different similarity distributions than raw-code embeddings). The right threshold may be lower (0.3–0.4) now that text vectors are semantically meaningful.

**Setting the threshold too high** → results are filtered out that should appear → lower recall → lower MRR.
**Setting the threshold too low** → noise leaks through → lower precision → but MRR is rank-based, so this matters less.

For MRR optimization: err slightly lower (0.3–0.4 is the expected sweet spot).

## Tasks

### Task 1: Trigger full re-index

Before running any benchmarks, the executor must ensure the Qdrant collection reflects the 11-02 and 11-03 changes.

**Steps**:

1. Confirm Docker + Qdrant are running:

   ```bash
   docker compose ps
   ```

2. Trigger a full re-index of the ia-framework repo itself (the framework indexes itself):

   ```bash
   ia-framework index --full
   # OR, if the CLI is not globally installed:
   pnpm --filter @ia-framework/cli tsx src/bin.ts index --full
   ```

3. Wait for indexing to complete. The CLI prints progress:

   ```
   ✓ Indexed N chunks from M files
   ```

4. Verify the collection has a sparse vector by checking `ia-framework status` or the dashboard `/api/status` endpoint. The `hasSparseVector` flag in `getCollectionInfo()` should be `true`.

**If re-indexing fails**: The most likely cause is the collection schema mismatch (old collection without `sparse` slot). Run `ia-framework index --full` which calls `initialize()` → dimension mismatch detection → collection recreation → fresh index. If this doesn't trigger recreation, manually delete the collection via Qdrant dashboard at `http://localhost:6333/dashboard` and retry.

### Task 2: Run threshold benchmark sweep

Run the `benchmark run` CLI command at four thresholds to find the optimal value. Each run should use the 30-query corpus from 11-01.

**Before running**: Verify the corpus is loaded:

```bash

```

If this exits with "corpus not found", check `.ia-framework/benchmark-queries.json` exists. If the corpus needs refreshing, re-run 11-01.

**Run the threshold sweep** (4 benchmark runs):

```bash

# Threshold 0.4 — likely sweet spot
ia-framework benchmark run --threshold 0.4 --label "threshold-0.4" --top-k 10

# Threshold 0.5 — current default (baseline for comparison)
ia-framework benchmark run --threshold 0.5 --label "threshold-0.5" --top-k 10

# Threshold 0.6 — strict
ia-framework benchmark run --threshold 0.6 --label "threshold-0.6" --top-k 10
```

**Record results**: Capture the MRR, Hit@10, and avgLatencyMs from each run's table output. You'll compare these in Task 3.

Expected MRR improvement from Phase 10 baseline (which had 3-query corpus, no prose text vectors):

- Prose text vectors alone: +15–30% MRR
- Threshold tuning: +5–10% MRR at optimal threshold
- Net combined improvement: +20–40% MRR vs pre-Phase-11 baseline

### Task 3: Compare runs and select optimal threshold

After all 4 runs, compare them:

```bash
# List recent runs to get run IDs
ia-framework benchmark list --limit 10

# Compare the 4 threshold runs (use short run ID prefix — 8 chars)
ia-framework benchmark compare <id-0.3> <id-0.5>
ia-framework benchmark compare <id-0.4> <id-0.5>
ia-framework benchmark compare <id-0.6> <id-0.5>
```

**Selection criteria** (in priority order):

1. **Highest MRR** — primary metric
2. **Highest Hit@10** — secondary metric
3. **Reasonable latency** — lower threshold means more results to rank, but should be < 500ms avg

**Expected outcome**: threshold 0.3 or 0.4 will likely win because:

- Prose text descriptions are more semantically distant from query text than raw code was from code queries
- Lower threshold allows semantically-relevant but slightly-different-phrasing results through
- The 30-query corpus has negative queries (expectedFiles=[]) which aren't harmed by lower threshold (they'll still return no results if the codebase genuinely doesn't have the content)

**Decision rule**: Choose the threshold with the highest MRR. If two thresholds tie on MRR (unlikely but possible), choose the higher one (less noise).

## Notes

- **No new tests needed in this plan** — the only code change is a constant in `search-codebase.ts`. The threshold value is already covered by the existing `searchCodebaseHandler()` tests which check that `scoreThreshold` is passed through correctly.
- **Commit separately**: Commit the benchmark runs (they're stored in `.ia-framework/benchmarks.sqlite` which is `.gitignore`'d) — no commit needed for them. Commit only the `search-codebase.ts` change and the planning file updates.
- **If Qdrant is not running**: Start it with `docker compose up -d qdrant` from the `ia-framework` root.
- **If the CLI isn't built**: Run `pnpm -w build` first to ensure `ia-framework` binary is up to date.
- **MRR for negative queries**: Negative queries (neg-01 through neg-05) have `expectedFiles: []`. The `BenchmarkRunner` treats these as `hit=false, reciprocalRank=0` regardless of threshold. This is correct — a true negative correctly scores 0. The threshold doesn't affect their ranking.
